01 · Executive Summary
01 Executive Summary

Extending Shivsena Live
to Android and iOS

Shivsena Live is being developed as a Marathi digital news and content platform. This proposal covers the development of its Android and iOS mobile applications — the layer that carries the platform directly into readers' hands.

The applications will connect to the existing WordPress CMS through APIs. This is the central design decision of the project: the editorial team continues to publish news exactly as it does for the website, and that content appears automatically inside both applications. There is no second content system to maintain, no duplicate publishing workflow, and no additional editorial burden created by adding mobile.

Both applications will be built on Flutter, which allows a shared application architecture while still producing genuinely native Android and iOS builds. One codebase is written, tested and maintained; two platform-specific applications are delivered.

What Readers Get

Users will be able to access main news, regional updates, politics, editorial content, sports, entertainment, trending content, Shiv Sena Corner content, videos, podcasts, photo galleries and web stories — organised through a mobile navigation structure designed for one-handed reading.

01

Content Reading

Home feed, categories, article detail, search and related content across the full section tree.

02

Multimedia

Video listing and playback, podcast episodes with audio controls, galleries and web stories.

03

Engagement

Push notifications, sharing to WhatsApp and social platforms, bookmarks and recently viewed.

04

Commercial

Advertising-ready placements across home, feed, article and section levels, plus analytics.

The Commercial Shape

The Android and iOS applications are individually priced, and a combined package price is offered for developing both together. Because the two applications share a Flutter codebase and a single API integration layer, developing them as one coordinated project is materially more efficient than running two separate builds.

03 · Technical Architecture
03 Technical Architecture

One Content Source,
Two Applications

Content flows in one direction — from the editorial desk, through the CMS and API layer, into both applications. Nothing is published twice.

Layer 1 · Source
Editorial Team

Reporters, sub-editors and the desk publish news, videos, podcasts, galleries and web stories through the interface they already use. No change to the existing editorial workflow.

↓
Layer 2 · Content Management
WordPress CMS

Remains the single source of truth for all content. Categories, tags, regional sections, media and special content pillars are all managed here — for the website and the applications alike.

↓
Layer 3 · Interface
WordPress REST API & Custom Endpoints

Standard REST endpoints are used where they are sufficient. Custom endpoints are built where the applications need shaped responses — a lighter home feed, combined section payloads, or media-specific structures that reduce round trips.

↓
Layer 4 · Application
Flutter Application

A single Dart codebase containing all screens, navigation, state handling, local caching and offline-state behaviour. Built once, compiled twice.

↓
Layer 5 · Distribution
Android & iOS Users

Native builds distributed through Google Play and the Apple App Store, each following its platform's own conventions for navigation, notifications and permissions.

Cloudflare / CDN

Serves images and static media from edge locations, reducing both app load time and origin server load.

Cloud VPS

04 · Technology Stack
04 Technology Stack

Why Flutter for This Project

A news application is largely the same product on both platforms — the same feed, the same article, the same player. Writing that twice, in two languages, for two teams, is where most mobile budgets are spent. Flutter removes that duplication while still delivering real native builds rather than a web page in a wrapper.

TechnologyRole in this project
FlutterCross-platform UI framework. One application architecture, screen set and component library shared across Android and iOS, compiled to native code on each platform — not rendered in a web view.
DartThe language the application is written in. Strongly typed and compiled ahead of time for release builds, which keeps startup and scrolling performance predictable on mid-range Android devices.
WordPress REST API
+ custom endpoints		The content interface. Standard endpoints for posts, categories, media and taxonomies; custom endpoints where the applications benefit from purpose-shaped responses that reduce the number of calls per screen.
Firebase Cloud MessagingPush notification delivery to both platforms. Supports targeted sends and, where technically feasible, category-based notification preferences controlled by the user.
Firebase AnalyticsEvent and screen tracking. Supplies the behavioural data needed to judge which sections perform, which notifications are opened and where readers drop off.
Image optimisation & cachingImages are resized and cached on device so repeated feed scrolling does not re-download the same assets. The single largest factor in perceived mobile news app speed.
API-based content syncContent is fetched on demand with pagination and pull-to-refresh, so new stories surface without the user reinstalling or waiting on an app update.
Deep linkingWhere applicable, shared article links open directly to that article inside the application rather than dropping the user on the home screen.
Android build / Google PlayProduction AAB generation, signing configuration and store submission assistance.
iOS build / App StoreProduction build generation, certificate and provisioning configuration, and store submission assistance.

What Shared Architecture Does and Does Not Mean

It does mean

  • One codebase written, reviewed and maintained
  • Feature parity across platforms by default
  • A fix applied once resolves it on both apps
  • Two genuinely native builds, not a web wrapper
  • Lower combined cost than two separate builds

It does not mean

  • Zero platform-specific work — iOS still requires its own build pipeline, certificates, device testing and store review
  • Identical behaviour everywhere — navigation, notification permissions and share sheets follow each platform's conventions
  • Half the cost of two apps — shared logic reduces effort substantially, but each platform is tested and shipped separately

13 · Performance & Security
13 Performance & Security

Built for Real Network
Conditions

A news application is used on moving trains, in low-signal districts and on mid-range handsets. The measures below are scoped for those conditions rather than for a lab.

Performance

API Caching

Responses cached to avoid repeat calls for content already fetched.

Image Optimisation

Right-sized images requested per screen density rather than full-resolution files.

Lazy Loading

Images and heavy elements load as they approach the viewport.

Pagination

Feeds load in pages rather than pulling an entire section at once.

Efficient API Calls

Calls batched and shaped to reduce round trips per screen.

Local Caching

Recently fetched content held on device where appropriate for faster return visits.

Optimised Startup

App startup path kept light so the first screen appears quickly.

Network Error Handling

Connection failures handled with a retry path, not a crash or blank screen.

Loading States

Visible loading indicators so the app never appears frozen.

Empty States

Designed empty states for sections or searches with no results.

Security

1

HTTPS / SSL

All communication between the applications and the API travels over encrypted connections.

2

Secure API Communication

API requests follow secure transport and request-handling practices appropriate to a public content API.

3

Secure Local Storage

Secure storage used for sensitive local information where such information is required.

4

Authentication Readiness

If a login capability is added in future, authentication security practices will be applied at that point. No login is part of this scope.

5

Basic API Security Practices

Standard protections applied on the application side of the API relationship.

6

Input Validation

User-supplied input, such as search queries, validated before being sent to the API.

7

Secure Configuration

Keys and configuration handled through release-appropriate practices rather than hard-coded in plain source.

A Realistic Statement

No application can be described as fully secure. These are sound, standard practices that reduce risk — not a guarantee against every possible threat.

!

Shared responsibility. Application-side security is scoped here. Server, CMS and API-side security — firewall rules, WordPress hardening, patching and access control — sit with the platform and hosting side of the project, not within this mobile application scope.
